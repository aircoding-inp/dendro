# Dendro 设计

## 它是什么

一篇论文只留下结论。想法怎么来的、哪些方向被否掉、每次实验的设置和日志、某个数字出自哪次运行，这些都不在正文里。
Dendro 把这些记成一条 research trace，论文只是它的一个视图。

名字取自年轮：树每长一季留下一圈，读年轮就能读出它怎么长大。

研究只是一种项目。任何项目的工作记录都一样有用：AI 收集、分析、整理，用来理清思路、记下问题，再生成报告、PPT 和讲稿。

## 三层

| 层 | 做什么 | 由谁 |
|---|---|---|
| 记录 | 把已有的记录抄进来：提交、改动、对话、发布、依赖、工单。所有项目一样 | 收集器，不用模型 |
| 理解 | 画像、每日 `digest`、`problem`、`decision`。每条都指回它读的记录 | agent |
| 产出 | 报告、演示、讲稿、周报、脉络。按需要写，每段指回记录 | agent，有人要时 |

记录越完整，后两层越可信；后两层可以重做，记录不能。

## 原则

1. **不给研究者增加负担。** 平台不要求人填任何东西。记录由 agent 在伴随工作时顺手完成，或者自己去收集。
2. **人只读，agent 写。** 因为第 1 条，界面上没有增删节点的入口。人说的话、做的决定，由听到它的 agent 代为记录，并标明是谁说的。
3. **只追加。** 事件写下后不改不删。改主意是一条新事件，指向它取代的那一条。
4. **状态是算出来的。** 论证图、进度、某一天的样子，都由事件回放得到，不单独存储。
5. **抄录和判断分开。** 收集器只抄录已有的记录，不做判断。把一句原话读成想法还是纠正、给一篇论文写总结，是 agent 的判断，
   记成另一条事件并指回原始记录。抄录可以完全自动；判断以后可以重做。
6. **每个实验连到论点。** 一个实验必须写明它回答的问题和会改变的决定，否则它不该被运行。

## 事件

一条事件是一个 JSON 对象，见 `dendro/schema.py`：

| 字段 | 含义 |
|---|---|
| `id` | 事件其余内容的哈希，内容一改 id 就对不上 |
| `ts` / `rec` | 事情发生的时间 / 被记录的时间；补录历史时两者不同 |
| `type` | 事件类型，见下 |
| `actor` | 谁做的：`human`、`agent` 或 `system` |
| `writer` | 哪个 agent 或适配器记下的 |
| `body` | 内容，按类型校验 |
| `about` | 涉及的节点 |
| `refs` | 指向更早的事件：`responds_to`、`based_on`、`supersedes` |
| `source` | 记录的出处，例如会话文件和消息 id |
| `prev` | 同一个 writer 的上一条事件 |

事件分两类，共用一条记录：

- **结构事件** 改论证图：`node.put`、`node.retire`、`edge.put`、`edge.drop`。只能由 agent 或系统发出。
- **过程事件** 记发生了什么：`said`、`idea`、`direction`、`correction`、`decision`、`design`、`survey`、`run.start`、
  `run.end`、`result`、`reading`、`commit`、`text`、`note`。人的事件只有前五种：`said` 是原话，其余四种是对原话的解读。

## 论证图

节点种类：`claim` 论点、`prior` 一类已有工作、`paper` 一篇论文、`method` 方法、`experiment` 实验、`run` 一次运行、
`resource` 算力、`section` 论文章节。
节点 id 是 `种类:名字`，例如 `experiment:barrier-a`。

| 关系 | 从 | 到 | 读作 |
|---|---|---|---|
| `gap` | prior、paper | claim | 这项工作留下了这条论点要补的缺口 |
| `covers` | prior | paper | 这一类工作里包含这篇论文 |
| `realized_by` | claim | method | 论点由这部分方法实现 |
| `tested_by` | claim、method | experiment | 由这个实验取证 |
| `of` | run | experiment | 这次运行属于这个实验 |
| `on` | run、experiment | resource | 跑在这台机器上 |
| `states` | section | claim | 这一节陈述这条论点 |
| `cites` | section | paper | 这一节引用这篇论文 |

实验和运行有状态：`proposed`、`approved`、`queued`、`running`、`done`、`failed`、`stopped`、`deferred`、`dropped`。

## 存储

```
<root>/dendro.json             项目名和格式版本
<root>/events/<writer>.jsonl   这个 writer 的事件，按记录顺序，每条指向上一条
<root>/blobs/<sha256>.<ext>    事件提到的文件，名字是内容的哈希
```

每个 writer 一个文件，两个 agent 同时写也不会碰同一个文件。读取时所有文件合并，按发生时间排序。`check` 校验每条事件的哈希、
每个文件的链，回放时每条事件是否成立，以及每个留存文件是否还是它名字说的内容。

运行日志、方法图这些文件放不进事件，所以按内容留存，节点的字段写 `{blob, name, bytes}` 指向它。原文件之后改了或删了，trace
里的这一份不变。

## 接口

两种，操作相同，写入被拒绝时都给出全部原因并且什么都不写：

- **命令行：** `python -m dendro`，所有输出是 JSON，被拒绝时退出码 2。
- **MCP 服务：** `python -m dendro mcp`，走标准输入输出，只用标准库。工具有 `dendro_state`、`dendro_overview`、`dendro_day`、
  `dendro_digest`、`dendro_profile`、`dendro_log`、`dendro_say`、`dendro_node_put`、`dendro_node_retire`、`dendro_edge_put`、
  `dendro_edge_drop`、`dendro_collect`、`dendro_check`。改图的工具没有“代某人”的参数，所以经由 agent 也无法以人的名义改图。
  仓库根目录的 `.mcp.json` 让在这个仓库里开的 Claude Code 会话直接连上。

平台自己的 agent 目前就是“接上这个 MCP 服务的任何 agent”。工具由模型调用，人不调用，模型要做什么由服务连接时算出的说明告诉它。
`install.sh` 和 `install.ps1` 把仓库放到 `~/.dendro/app`，再运行 `connect`：给机器上找到的 Claude Code 和 Codex 配好 MCP 服务、Stop
钩子和技能，都指向运行它的那个 Python，不用另外安装 Python 包。重新运行就是更新。仓库本身也是一个 Claude Code 插件（`.claude-plugin/`、
`hooks/`）。

## 自己运转

MCP 服务不能自己启动，也不能叫醒模型，所以收集和阅读分开：

- **收集不靠模型。** 没有给 `--root` 时，`mcp` 和 `hook` 自己找到所在项目：有 `./trace` 就用它，否则用 `~/.dendro/` 下的目录，
  第一次用时建好，不往项目里加文件。服务启动和每轮结束时收集提交、改动的文件和会话。每条记录保留它发生的时间，所以没开会话的
  一天，下次连接时仍然落在当天。
- **阅读靠连接时的说明。** 服务算出最近七天里有工作、但还没有 `digest` 的日子，每次最多三天，以及画像是否缺失或过期，写进
  MCP 的 instructions。agent 先回答用户，再在同一轮里补上，有子 agent 就交给子 agent。今天还没结束，不算。

收集多个会话同时运行时靠锁文件排队：每个写入者一把，收集一把，进程死后留下的锁一分钟后作废。

## 不猜

`digest`、`profile`、`problem`、`resolved` 和 `output` 是 agent 的阅读，核心替它们把关：

- `digest` 必须指向它读的事件，事件必须属于那一天。它可以同时带上当天的问题、决定和了结，要么全部写入，要么全部不写；这些事件的
  时间紧跟它们依据的记录，所以落在事情发生的那天，不是被读到的那天。
- `problem` 必须指向显示它的记录。`resolved` 用 `responds_to` 指向它了结的问题，并写明 `solved` 或 `dropped`。一个问题是否还开着，
  由事件算出。
- `output` 的每一段必须指向它依据的事件或项目里的文件，事件必须存在，文件按当时的内容留存。新版用 `supersedes` 取代旧版。
- `reply` 是 agent 说的话，不是事情发生过的证据。
- `profile` 的每条事实写明依据：`record`（记录里写着）、`inferred`（从记录读出）、`unknown`（记录没说）。前两种必须有出处，
  `unknown` 不能有值。出处是事件，或者项目里的文件；文件按当时的内容存进 `blobs/`。

## 产出

`dendro_material` 按种类（`report`、`slides`、`speech`、`weekly`、`thread`）返回写作指南和这段时间的材料：画像、日记、决定、问题、结果、
发布、参考、以前写过的同类产出，放不下的会说明少了多少，有工作却没读过的日子也列出来。`dendro/guides/` 是指南，先列提纲再动笔，
写完逐条核对。`dendro_output` 把结果存进 trace；PPT 这样的文件作为 `blobs/` 留存。之后又有新记录时，页面和 `dendro_overview` 都会
说明，所以旧报告不会被当成现状。

Claude Code 和 Codex 里 `skills/dendro-report` 在有人说写报告、做 PPT、讲稿、理清思路时触发；其他客户端用 MCP 的 prompts，或者靠连接
说明里的一句话。

## 项目类型

画像写明 `family`：`research`、`software`、`work` 或 `other`。这只决定显示用的词，存储的种类不变：同一个 `experiment` 节点，研究项目里
叫实验，软件项目里叫验证，日常工作里叫任务。没有内容的视图不出现，所以没有实验的项目就没有实验页。

## 网站（只读）

`python -m dendro serve ROOT...` 在本机打开网站，每次刷新读到的都是 trace 当前的样子；`export` 把同样的页面和数据写进一个
文件夹。页面在 `dendro/site/index.html`，没有任何写入入口，服务器只回答读取。

`serve` 只听本机。上线用 `export --public` 生成静态文件，放到任何静态托管上，所以公网上没有运行中的服务。`--public` 不改 trace，
只是不展示：没有 `said`，没有来源，没有本地路径，没有算力节点，留存文件只带图片，并写一个不让搜索引擎收录的 `robots.txt`。对原话的
解读和论文正文仍然在里面，发布前要由人看过。`serve --public` 可以先预览。

左边选项目和视图，底部是时间，右边是详情抽屉。每个视图显示的都是所选那一天结束时的样子。地址栏记着项目、视图、日期和选中的
对象，可以直接发给别人。键盘：左右键换日期，数字键换视图，`/` 筛选，`Ctrl K` 搜索全部，`Esc` 关闭。

| 视图 | 显示什么 |
|---|---|
| 年轮 | 项目的截面，一天一圈，圈宽是这天的记录量，事件是圈里的点；旁边是项目是什么、当天的数字和日记、未解决的问题、论点和它的证据、人说的话、最新的产出 |
| 论证 | 项目是一棵从已有工作里长出来的植物，悬停点亮它依靠的和依靠它的部分。没有论证图的项目是脉络：决定、纠正、问题、了结和发布按时间排开 |
| 记录 | 这一天发生的事，解读嵌在它读的那句话下面 |
| 问题 | 没解决的大而靠前，了结的退到后面，写着怎么了结的 |
| 成果 | 写过的产出，演示按幻灯片排，每段旁边的数字点开是它依据的记录，后来有新记录时标出 |
| 实验 | 实验按在做、待定、已结分列；运行可排序，勾选几次可以对比设置 |
| 论文 | 目录和排好的正文，表格和图照原样；引用、依据标注和比前一天改动的段落都标出；有来源的数字点开看它来自哪次运行 |
| 文献 | 按年份，可按已有工作的分支筛选；另列项目链接的仓库和声明的依赖，没有文献节点时全部来自 `reference` 事件 |
| 算力 | 每台机器的硬件、用途、接下来的实验，以及运行的时间条 |
| 详情抽屉 | 节点的字段、方法图、关系和有关记录；运行分成结果、设置、日志、记录；事件的全文、出处、依据和后续 |

### 视觉

外观来自读木头。时间不是一条坐标轴，而是一根取样木芯：年轮是早材和晚材交替的带，右端是树皮，再往右是还没长出来的部分。
首页是树的截面，形状由项目名决定，所以每个项目有自己的样子，这个截面缩小后就是项目的头像。

颜色都是树里有的东西：底色是沼泽橡木（暗）或边材（亮）；唯一鲜亮的颜色是形成层，树上唯一活着、还在生长的一层，所以它只
用在现在、选中和进行中；树脂是待定，火疤是失败，霜轮是被人纠正。状态图标是一圈圈的年轮：虚线是还没批准，转动的弧是正在
跑，实心的轮是长成了。

正文用衬线，界面用无衬线，数字用等宽，最小 13px。

### 论证是一株植物

我们站在已有工作的土地上生根发芽。土里的石头是一类已有工作，颗粒是论文，根是它留下的缺口；种子在地面上，主枝是论点，分枝是
方法，叶是实验。在做的叶子是形成层的颜色，完成的是成熟的叶，待确认的是树脂色的芽，后置的是虚线的芽，失败、停止和放弃的枯叶
落到地上。每次结束的运行是地上的一片落叶，落得越多腐殖层越厚，这就是落叶归根。

形状由项目有过的全部节点决定，所以一个节点每天都在同一个位置，时间条只决定长到了哪里；枝条的粗细是它撑着多少东西。一个实验连着
多个方法时长在最先连上的方法上，其余的关系悬停时显示。

打开详情抽屉不改变植物的形状，视野平移到选中的部分。手机上先看到整株，点一下放大到那里，点空地退回。

动的东西都由时钟算出：第一次打开时依次生根、抽枝、展叶；日期前进时只长新东西，后退时收回去；平时有缓慢的风和偶尔穿过全场的阵风，
养分从根走到进行中的叶，阵风过后完成的叶上偶尔飘下一片。系统设置减少动态时只显示静止的植物。

### 数字的来源

论文里的数字可以连到运行：一条 `reading` 事件，`about` 写章节和运行，`data` 写 `{quote, field, value}`，`quote` 是论文源码里
这段文字，`field` 是运行数据里的路径。页面把这段文字变成链接，并比较 `value` 和运行现在的值；对不上时标红。论文改了之后，
`quote` 找不到的链接不再显示。表格搬到别的章节，由 agent 写新的 `reading` 指向新章节。

## 收集

平台有自己的 agent，它用两种方式取得记录，都不需要人动手：

- **伴随：** 研究会话进行时，agent 把当下发生的事记下来，例如一个决定和它回应的那句话。`dendro hook` 接在 Claude Code 的
  Stop 钩子上，每轮结束时收走这个会话里人打的字；收不到时不打断会话。
- **自己收集：** 运行收集器，把已经存在的记录抄成事件，再阅读它们，补上解读。`files` 收集器只记路径、大小和时间：git 仓库里是
  还没提交的改动，其他文件夹是所有文件。两次收集之间发生的事、第一次之前删掉的文件，都没有记录。

一个会话可以在几个项目之间移动，所以每条消息按它当时的工作目录归到所在项目，别的项目里说的话不算进来。

收集器在 `dendro/collect/`。每条收集来的事件带来源键（来源种类加记录 id），同一条记录再收集一次不会重复。

对话只是来源之一，而且是最不可靠的一种。能从真实记录里读到的，就从真实记录里读：实验跑了什么看作业目录和台账，代码改了
什么看 git，论文写了什么看论文源码。

| 收集器 | 来源 | 得到 |
|---|---|---|
| `claude-session` | Claude Code 会话记录里人打的字，和 agent 每轮最后的结论 | `said`，`reply` |
| `codex-session` | Codex 的 rollout，人坐在跟前的会话才读，`codex exec`、服务和子 agent 的提示词不是人说的话；格式 OpenAI 不保证，读不懂的跳过 | `said`，`reply` |
| `bibtex` | 文献库 | `paper` 节点 |
| `git` | 仓库的提交 | `commit`，带作者、改动文件和行数 |
| `releases` | 仓库的标签 | `release` |
| `references` | 依赖清单、`.gitmodules`、笔记里的 GitHub 和 arXiv 链接、`.bib` | `reference`，分 `dependency`、`repository`、`paper`；版本变了是新记录 |
| `github` | 通过 `gh` 读 issue、PR 和失败的 CI，只读，最多一小时一次，从不在连接时等它 | `ticket`（开、关、合并各一条），`check` |
| `latex` | 论文源码 | `section` 节点，存正文（不带参数的宏写开）、词数、待填数、依据标注和它在正文里的位置、留存的图；`cites` 边 |
| `items` | 项目自己的导出程序写好的条目，每行一条 | 任意事件 |
| `file` | 属于某个节点的文件，例如运行日志、方法图 | 留存这个文件，写进节点的字段 |

实验记录的格式每个项目都不同，所以核心不去理解它：项目写一个自己的导出程序，把台账和作业目录转成条目，再用 `items` 收进来。
导出程序放在 `tenants/<project>/`：每个作业变成一个 run 节点，带设置和结果，它跑的 GPU 变成 resource 节点。

边的一端还不在图里时，这条边留到下次运行再写。

agent 的解读，已经手工做过、之后要自动化的：把 `said` 读成 `idea`、`direction`、`correction`、`decision`；给 `paper` 写 `survey`
并连到它留下缺口的论点。
